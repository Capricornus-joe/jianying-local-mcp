# 性能与基准

0.3.0 通过批量保存、紧凑返回和进程内媒体元数据缓存减少重复工作。下面是三轮真实 MCP stdio 调用的结果；它衡量本地管理工程编辑，不包含剪映原生渲染。

## 测试方法

输入为 100 条合成字幕和一份 105 秒的静音 WAV。两种方式从同一源管理工程执行五步修改：改字、加粗、渐显、统一字号、描边。

- 逐步方式：依次调用五个既有编辑工具，每一步生成新修订，并显式请求完整计划。
- 批量方式：一次 `batch_edit` 完成相同步骤，使用默认紧凑返回。
- 两组使用同一份 0.3 实现；对照不是历史版本二进制。初始工程创建、MCP 客户端启动以及测量后的读取验证不计入编辑时间。
- 比较最终片段的语义时，将各修订复制后的媒体路径规范化；每轮均确认最终片段等价、失败批次零写入、默认紧凑返回和分页正常。

测试只生成临时合成媒体和管理工程，结束后删除临时目录，不调用剪映应用或发布工程。

## 三轮中位数

| 指标 | 逐步保存、全量返回 | 一次批量、紧凑返回 |
|---|---:|---:|
| 编辑工具调用 | 5 | 1 |
| 新增修订 | 5 | 1 |
| 复制媒体字节 | 50,400,220 | 10,080,044 |
| MCP 响应字节 | 205,234 | 2,273 |
| 编辑执行时间 | 0.2302 秒 | 0.03041 秒 |

在这个小样中，媒体复制量减少 80%，响应字节减少 98.89%，所测编辑阶段约快 7.57 倍。三轮逐步耗时分别为 0.2355、0.2248、0.2302 秒；批量耗时分别为 0.03094、0.03041、0.03009 秒。完整数据见 [performance-v03.json](performance-v03.json)。

响应按序列化后的 MCP `CallToolResult` 的 UTF-8 字节计数，包含 text 与 structured content。**这不是计费 tokens 或费用统计。** 该对比同时改变保存次数和返回方式，不能把全部收益单独归给其中一项。

结果不包括模型响应、启动剪映、原生渲染、导出、媒体来源创建或人工审看。实际收益随片段复杂度、媒体体积、磁盘、缓存状态和调用方式变化；不能将该小样比例推广为整个视频制作流程的提速。

## 复现

在仓库根目录安装依赖后运行：

```sh
python -m pip install -e '.[test]'
python scripts/benchmark_v03.py
```

脚本执行三轮真实 stdio 调用，自动清理临时项目，并将当前结果写入 `docs/performance-v03.json`。因此重新运行会覆盖该记录文件。它不依赖私人素材、已生成演示工程或本机剪映客户端配置。

## 实现带来的边界

- `batch_edit` 仍保留每一步校验，只在最后创建一个修订；不会生成五份中间工程。它不支持发布和原生导出。
- 写入默认不回传完整 plan；`read_managed_project` 默认摘要。分页按 clip 数量限制，不是硬性字节限制；需要全文时仍可显式读取。
- 元数据缓存只存在于一个服务进程中，最多 2048 项、每项最多五分钟；键含媒体路径、文件身份与 FFmpeg 身份。并发的同一探测可合并，失败结果不缓存。重启进程或文件变化后重新探测，不持久缓存媒体内容。
- 批处理的 `review_scope` 只是变更范围提示。自动按范围渲染/验收、单个已发布工程的增量更新，以及 Mac 自动导出尚未实现。

375 项测试和 60 个子测试的发行回归记录，以及基准中的语义比较，证明的是程序行为；原生画面、声音与可编辑性范围另见[兼容性说明](compatibility.md)。
